# 我们以为 prompt cache 没用, 一年后省了 60%

> 这是一个关于"读文档要读第三遍"的故事. 一个我们团队拖了大半年才上的小改动, 上线后单请求成本下降 60%, P50 延迟从 1.8 秒降到 740 毫秒. 但更值钱的不是那个 60%, 是 "我们之前为什么坚信它没用" 这一段.

## 引言

去年这时候, 团队里讨论过两次要不要上 Anthropic 的 prompt cache. 两次都被我们自己否了.

理由听起来挺有道理: "我们 prompt 经常改, cache 命中率肯定低", "我们流量结构不规整, cache 过期得比命中还快", "上了之后 prompt 改一行就要重算, 不划算".

四月底我们还是上了. 然后一个完整的对照月下来: 单请求成本 -60%, P50 延迟 -59%, P95 延迟 -62%, hit rate 稳态 71% 到 74%. 月账单当月就跌了 59.4%.

不是模型变了, 不是我们重写了什么底层, 就是改了一下 prompt 的拼接顺序.

下面这一段是 "我们之前为什么这么蠢" 的部分. 我觉得它比 60% 这个数本身更值得写出来.

![一张账单从高到低的折线图](#image-prompt-1)

## 一、我以前为什么不上 cache

我自己是那两次否决里反对得最坚决的那个.

我的论点听起来无懈可击: prompt cache 是 "你写一遍, 后面打折". 我们 prompt 又不固定 — 用户问题千变万化, 系统说明每周都在调, 工具定义还在加. 这种东西怎么 cache.

听起来像在说"这件事不适合我们". 但实际上, 它是一个**没读完文档的人在替读完文档的人下判断**.

我们工程师有个职业病: 看到"缓存"两个字, 脑子里默认想到的是 key-value cache — 同一个 key 来一次, 命中, 返回. 同一个 key 来第二次, 还在 TTL 内, 命中, 返回. key 哪怕差一个 token, miss, 全部重算.

如果 prompt cache 真是这个机制, 我那个反对是对的. 但它不是.

## 二、文档里那个被我忽略的细节

Anthropic 的 prompt cache 是按 **prefix** 算的. 不是按整个 prompt 内容算.

意思是: 你的请求被分成"前缀 + 后缀"两段. 前缀那段, 只要内容字节级一致, 就命中 cache. 后缀那段, 随便变, 不影响前缀命中.

这一个细节, 把整个判断翻过来了.

我们之前的 prompt 是这样拼的:

```
system:
  你是一个 ...助理. 当前用户问题: {user_query}. 当前会话上下文: {context}.
  工具定义: {tools}.
```

注意, user_query 和 context 被塞进了 system. 每次请求, system 都在变. prefix 永远没法稳定 — cache 命中率为 0.

我们改完之后是这样:

```
system: 你是一个 ...助理. (固定不变, 3500 token)
tools: {tools}  (固定不变)
user: 当前会话上下文: {context}. 当前问题: {user_query}.
```

system + tools 这两段固定下来, 总共大概 4000 token. 这 4000 token 就是 prefix. 每次请求, 这 4000 都命中. 后面 user message 怎么变都不重算前缀.

就这一个改动. 不是换模型, 不是降级, 不是换 SDK. 单纯重排 prompt 拼接顺序.

## 三、重写 prompt 之后发生了什么

上线第一天到第七天, hit rate 从 0 爬到 72%, 然后就稳定下来了, 之后一个月在 71% 到 74% 之间晃.

具体数据 (生产环境同流量对照, 不是 staging 测试):

| 指标             | 上线前    | 上线后    | 变化      |
| ---------------- | --------- | --------- | --------- |
| 单请求 LLM 成本  | 100%      | 40%       | **-60%**  |
| P50 latency      | 1820 ms   | 745 ms    | **-59%**  |
| P95 latency      | 4200 ms   | 1610 ms   | **-62%**  |
| Cache hit rate   | 0%        | 71-74%    | -         |
| 月账单 (同流量)  | 100%      | 40.6%     | **-59.4%**|

中间那段 P95 的下降比 P50 更猛, 是因为我们的长尾请求恰好是 "前缀稳定 + 后缀长" 的那一类 — 这类请求以前重算整个长 prompt 重得慢, 现在前缀走 cache, 真正算的是短的那一段.

## 四、你能复刻多少, 取决于三个前提

我必须在这里写一段不那么招人喜欢的话, 不然这篇就成了"复制即可省 60%"的标题党.

我们能省到 60%, 不是因为 cache 是银弹, 是因为我们恰好满足三个条件:

1. **system prompt 比较长** — 我们的固定前缀大概 3500 token. 如果你 prompt 总长才 800 token, cache 给你省的比例就低得多, 因为 cache write 那 1.25x 的开销摊不薄.
2. **QPS 够高** — Cache 有 TTL, 流量太稀 cache 会在被命中之前先过期. 我们 production QPS 高, 这个问题不存在; 你如果是小流量场景, 收益会缩水.
3. **prompt 结构以系统说明为主** — 如果你每次请求都改前缀 (比如把用户名拼进 system), 前面所有努力都白费.

如果你的场景不满足这三条, 你大概率省 20-30%, 不是 60%. 这是数学, 不是悲观.

## 五、我们试过但没上的另外两条路

写到这里有一个反问绕不开: "那你为什么不做请求级 KV 缓存, 不做 Redis 缓存整个 response".

试过. 都没上.

- **请求级 KV cache**: 同一个 query → 同一个 response. 听起来更猛, 实际上对话场景里同一个 query 几乎不会重复出现, hit rate 长期低于 5%. 维护成本 > 收益.
- **Redis 缓存整个 response**: 太脆. 模型版本一升, 全部 invalidate. 一条 prompt 调一个字, 全部 invalidate. 我们短暂上过两周, 出过一次 cache 污染事故, 撤了.

Anthropic 的 prompt cache 比这两个都"笨"一点 — 它只 cache prefix, 不 cache response. 但**正是这个"笨", 让它在我们 prompt 调整频繁的现实里能稳态运行**.

很多时候选型不是选最强的那个, 是选最不容易出事故的那个.

## 结语

一年前我们说 prompt cache 没用. 一年后它替我们省下足够整团队按月一杯奶茶的钱.

不是它变了, 是我们终于读完了那段我们以为读懂了的文档.

如果你也有一个被自己否决过两次的 "我们这场景不适用" 的功能, 也许它值得被打开重新读一遍 — 第三遍.

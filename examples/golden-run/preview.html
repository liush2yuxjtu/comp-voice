我们以为 prompt cache 没用, 一年后省了 60%

技术内容池 · 2026-05-15 · 阅读约 6 分钟
这是一个关于"读文档要读第三遍"的故事. 一个我们团队拖了大半年才上的小改动, 上线后单请求成本下降 60%, P50 延迟从 1.8 秒降到 740 毫秒. 但更值钱的不是那个 60%, 是 "我们之前为什么坚信它没用" 这一段.

引言

去年这时候, 团队里讨论过两次要不要上 Anthropic 的 prompt cache. 两次都被我们自己否了.

四月底我们还是上了. 然后一个完整的对照月下来: 单请求成本 -60%, P50 延迟 -59%, P95 延迟 -62%, hit rate 稳态 71% 到 74%. 月账单当月就跌了 59.4%.

不是模型变了, 不是我们重写了什么底层, 就是改了一下 prompt 的拼接顺序.

[配图位 1] 一张账单从高到低的折线图

一、我以前为什么不上 cache

我自己是那两次否决里反对得最坚决的那个. 我的论点听起来无懈可击: prompt cache 是 "你写一遍, 后面打折". 我们 prompt 又不固定 — 用户问题千变万化, 系统说明每周都在调, 工具定义还在加.

听起来像在说 "这件事不适合我们". 但实际上, 它是一个没读完文档的人在替读完文档的人下判断.

二、文档里那个被我忽略的细节

Anthropic 的 prompt cache 是按 prefix 算的. 不是按整个 prompt 内容算.

我们改完之后是这样:

system: 你是一个 ...助理. (固定不变, 3500 token)
tools: {tools}  (固定不变)
user: 当前会话上下文: {context}. 当前问题: {user_query}.

就这一个改动. 不是换模型, 不是降级, 不是换 SDK. 单纯重排 prompt 拼接顺序.

四、你能复刻多少, 取决于三个前提

我们能省到 60%, 不是因为 cache 是银弹, 是因为我们恰好满足三个条件: (1) system prompt 比较长; (2) QPS 够高; (3) prompt 结构以系统说明为主.

如果你的场景不满足这三条, 你大概率省 20-30%, 不是 60%. 这是数学, 不是悲观.

五、我们试过但没上的另外两条路

请求级 KV cache 与 Redis full-response cache 都试过, 都没上. Anthropic 的 prompt cache 比这两个都 "笨" 一点 — 它只 cache prefix, 不 cache response. 但正是这个 "笨", 让它在我们 prompt 调整频繁的现实里能稳态运行.
